# SafeRadar AI

A women's travel-safety web app. People report incidents, see estimated risk on a map, compare routes, and share their live location with trusted contacts in an emergency. A machine-learning model estimates risk by place and time of day, and a text classifier suggests a category for each new report.

> **Please read first.**
> * **All data in this project is synthetic.** The incidents, the zones and the model scores were generated for development. They say nothing about how safe any real place is.
> * Risk levels are **estimates that compare places and times inside the training data**. "Low" never means safe, and a place with no estimate is **unknown**, not safe.
> * SafeRadar AI is **not an emergency service**. In an emergency, call 112.

## Features

| Area | What it does |
|---|---|
| Accounts | Registration and login with hashed passwords, user and admin roles, profile, up to five trusted contacts |
| Incident reports | Form with a map pin, severity and time. Reports are reviewed before anyone else sees them, and are shown without the reporter's name. Map points are rounded to about 110 m |
| Text classification | A logistic-regression model suggests a category (Harassment, Stalking, Threats, Unsafe surroundings). When it is not sure it says so and leaves the category for an administrator |
| Risk model | A Random Forest estimates a relative risk level (Low, Moderate, High) for each 550 m grid square, time of day and weekday or weekend |
| Heatmap | Leaflet map with the model's risk squares, report markers coloured by severity, and a time-of-day selector. Areas with no estimate are left uncoloured |
| Route planner | Up to three routes from OSRM, each scored by the risk model for the departure time. A route is suggested only when the data supports it |
| Emergency SOS | A private live-location link for contacts, with an automatic expiry. The app prepares text and WhatsApp messages but never sends them |
| Admin dashboard | Statistics, a review queue (approve, reject, set the category), and account deactivation |

## Technology

Python, Flask, Flask-SQLAlchemy (SQLite), Flask-Login, Flask-WTF, scikit-learn, pandas, NumPy, NLTK (stemmer only), Matplotlib, Leaflet and OpenStreetMap, OSRM for routing, Bootstrap 5, pytest.

## How it works

1. A user submits a report. The text classifier may suggest a category. The report is **pending**.
2. An administrator opens **Admin > Reports**, checks the text and the category, and approves or rejects it. Approving needs a category. Every review records who decided and when.
3. Approved reports appear on the dashboard and heatmap. Approved reports are shown without text or reporter, with rounded coordinates.
4. The risk model is trained offline from a cleaned dataset. The web app loads the saved model and uses it for the dashboard card, the heatmap squares and route scoring. If no model file exists, the app still works and says "no estimate yet".

## Data

**All data in this project is synthetic.** It was generated by `python -m scripts.prepare_data` so the machine-learning pipeline could be built and tested without collecting real reports about real people.

* Every generated row carries `is_synthetic = True`, and the pages, charts and metric files say so.
* The eight **Demo Zones** (market, bus stand, railway area and so on) are generic labels placed around the map centre. **They are not real neighbourhoods.** The busy hours, incident mix and severity attached to them are rules written by the developer.
* Because the patterns were written into the generator, the models can only learn those rules back. Their scores show how well the pipeline works, **not how well it would predict real-world safety**.
* The generator also adds deliberate defects (missing values, duplicates, bad coordinates, a future date) so the cleaning step has real work to do. The cleaning report says exactly what was fixed or dropped. Nothing is guessed: a missing severity is dropped, never replaced by an average.
* The seed script `python -m scripts.seed_demo_incidents` loads the synthetic rows into the database as approved demo reports so the maps have something to show. They are labelled "Synthetic demo data" and are kept apart from real reports in the admin pages. `--remove` deletes only synthetic rows.

## Machine learning

Both models use only the synthetic data described above. All numbers below were measured in the author's run and are repeated in `ml_models/risk_metrics.json` and `ml_models/nlp_metrics.json`.

### Risk model

* The study area is cut into 550 m grid squares, and the day into four slots (morning, afternoon, evening, night), weekday or weekend.
* For every square, slot and day type, the severity of reports is summed and divided by the number of days. The scores become three levels (Low, Moderate, High) using cut-offs taken from the **training period only**. The levels are relative.
* Only squares with at least 8 training reports are modelled (40 squares in this run). Everywhere else is **unknown**.
* The data is split **by time**: the model learns from the earlier part and is tested on the later part (test period 24 August to 14 November 2026).

| Model | Accuracy | Macro F1 |
|---|---|---|
| Majority guess (no learning) | 0.541 | 0.234 |
| Persistence guess (no learning) | 0.472 | 0.446 |
| Decision Tree | 0.422 | 0.406 |
| **Random Forest (used)** | **0.494** | **0.465** |

The Random Forest beats a blind guess on macro F1 but only slightly beats the simple persistence guess. With about 1,400 incidents each square and slot has only a handful of reports, so the labels are noisy.

### Text classifier

* TF-IDF features and logistic regression, with a naive Bayes model as a comparison. The 1,381 synthetic reports come from only 19 sentence templates.
* A normal random split scores a perfect 1.0, because the same template appears on both sides. That figure is **inflated** and is shown only to explain the problem.
* The honest evaluation keeps every template entirely inside either training or testing (grouped cross-validation):

| Model | Accuracy | Macro F1 |
|---|---|---|
| Majority guess | 0.338 | 0.126 |
| Naive Bayes | 0.416 | 0.438 |
| **Logistic regression (used)** | **0.395** | **0.413** |

* A second check uses 32 sentences written by hand in different wording: accuracy 0.75. With only 32 sentences this is a rough indication, not a reliable figure.
* The model's confidence did **not** track how often it was right, so the app never shows a percentage. It shows "Suggested", and an administrator confirms every category.

## Privacy and safety design

* Passwords are stored only as salted hashes. Forms are protected against CSRF, and report text is escaped when shown.
* Public pages never show report text or reporter details. Map coordinates are rounded to about 110 m.
* Administrators see a reporter only as "User #id". They never see live SOS locations, only counts.
* Report text is never written to the logs. Routing start and end points are never logged or saved, and error messages never include them.
* **SOS cannot send messages.** It creates a private link. The person sends it from their own phone using buttons that open their messaging app. The app never claims a message was delivered.
* An SOS link is unguessable, is marked private (no caching, no search indexing, no referrer), shows only a first name and the latest location, expires after 4 hours, and stops showing a location the moment the person stops sharing. The saved location is erased when an alert ends.
* One live alert per person, and at most five alerts per hour.

## Known limitations

* The data and the models are synthetic (see Data). The scores do not describe real safety.
* The risk model covers only the squares near the map centre that have enough reports. A route outside that area gets "not enough data".
* The public OSRM demo server gives **driving** routes only, so times are driving times. A server with a walking profile can be set in `.env`.
* SOS location updates continue only while the SOS page stays open in the foreground. The link works for people outside your network only when the app is deployed (or reached through a public address set as `PUBLIC_BASE_URL`).
* The text classifier handles English only.
* The saved models are loaded with `joblib`. Only load model files you created yourself.

## Getting started (Windows PowerShell)

```powershell
git clone https://github.com/vaishnaviD1509/SafeRadar-AI.git
cd SafeRadar-AI
python -m venv venv
.\venv\Scripts\Activate.ps1
pip install -r requirements.txt
copy .env.example .env
```

Open `.env` and set `SECRET_KEY` to a long random string. You can create one with
`python -c "import secrets; print(secrets.token_hex(32))"`.

Create the database and an administrator:

```powershell
flask --app run init-db
flask --app run create-admin
```

Create the synthetic data, train the models and load the demo reports:

```powershell
python -m scripts.prepare_data
python -m scripts.run_eda
python -m scripts.train_risk_model
python -m scripts.train_classifier
python -m scripts.seed_demo_incidents
```

Start the app and open http://127.0.0.1:5000:

```powershell
python run.py
```

On macOS or Linux, activate the environment with `source venv/bin/activate` instead.

## Using the app

* **Visitor:** register and log in.
* **User:** dashboard, report an incident, heatmap, route planner, profile and trusted contacts, SOS.
* **Administrator:** the **Admin** link. **Overview** shows the numbers, **Reports** is the review queue (open a report, confirm the category, then approve or reject), and **Users** lets you deactivate or reactivate accounts.

Browsers share location only on `localhost` or HTTPS, so open the app as `http://127.0.0.1:5000` or `http://localhost:5000` while developing.

## Command-line tools

| Command | What it does |
|---|---|
| `flask --app run init-db` | Create the database tables (safe to repeat) |
| `flask --app run create-admin` | Create an administrator, or promote an existing user |
| `flask --app run review-report <id> approved\|rejected\|pending` | Review a report from the command line (a backup to the admin pages) |
| `flask --app run classify-reports` | Suggest categories for reports that have none |
| `flask --app run purge-sos [--keep-days 30]` | Erase the saved location of ended or expired SOS alerts and delete old ones |
| `python -m scripts.prepare_data` | Generate and clean the synthetic dataset |
| `python -m scripts.run_eda` | Draw the exploratory charts |
| `python -m scripts.train_risk_model` | Train and evaluate the risk model |
| `python -m scripts.train_classifier` | Train and evaluate the text classifier |
| `python -m scripts.seed_demo_incidents [--remove]` | Load (or remove) the synthetic demo reports |

## JSON endpoints

All need a logged-in user, and are never cached.

| Endpoint | Purpose |
|---|---|
| `GET /api/risk?lat=&lon=[&when=]` | Risk estimate for a place and local time |
| `GET /api/risk-grid[?slot=&weekend=]` | Heatmap squares for a time slot |
| `GET /api/route?from_lat=&from_lon=&to_lat=&to_lon=[&when=]` | Routes scored by risk |
| `POST /sos/start`, `POST /sos/<id>/update`, `POST /sos/<id>/end` | SOS life cycle (owner only) |
| `GET /share/<token>`, `GET /share/<token>/location` | Public SOS pages (no login, private link) |

## Testing

```powershell
python -m pytest -q
```

The suite has more than 350 tests. Besides unit tests for every module, it includes an end-to-end test that walks through registration, reporting, admin approval, the maps, route planning and SOS, and a smoke test that opens every page as a visitor, a user and an admin. Tests use a fake routing service, so they need no internet connection.

## Deployment notes

* Set a strong `SECRET_KEY` and `APP_ENV=production`. Serve over HTTPS: browsers only share location on secure pages.
* Set `PUBLIC_BASE_URL` to your public address so SOS links open for your contacts.
* The public OSRM server is for light use. Run your own OSRM server for real traffic, and use a walking profile for pedestrian routes.
* Run `flask --app run purge-sos` regularly (for example daily).
* SQLite is fine for development. Use a production database via `DATABASE_URL` for real use.
